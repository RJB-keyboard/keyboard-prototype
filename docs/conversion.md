# オフラインかな漢字変換

[READMEに戻る](../README.md) · [全体設計](architecture.md) · [開発手順](development.md)

`SumireKanaKanjiConverter.open(context)` は、同梱辞書を読み込み、
`convert(reading, limit)` でかな漢字交じりの候補を返す。
`convertCandidates(reading, limit)` は表記とスケール済みの変換コストを返す。
この処理にも、文脈を読みへ戻す `readingOf(text)` にも LLM・ネットワークは使わない。
初期化・変換は IME の単一ワーカーで実行する。

## 採用したエンジンとデータ

変換には [KazumaProject/kotlin-kana-kanji-converter](https://github.com/KazumaProject/kotlin-kana-kanji-converter)
の **実行時部分を Android 向けに移植・修正したコード**を使用する。
上流そのままのバイナリでも、完全な Mozc エンジンでもない。
上流の LOUDS 読み／表記トライ、単語コスト・品詞接続コスト、ラティス構築を利用し、
そのラティス上で Viterbi/A* による N-best 変換を行う。

- 固定版: `v1.7.252`
- ソース commit: `a1c44cc6f104e381056c0acc42d8d22a36a5918c`
- 実装: `app/src/main/java/com/kazumaproject/`
- 辞書: [公式リリースの japanese_keyboard_dictionary_assets.zip](https://github.com/KazumaProject/kotlin-kana-kanji-converter/releases/tag/v1.7.252)
  から抽出した `system` 3 ファイル、品詞表、接続行列の計 5 ファイル。
- 辞書の抽出後 ZIP は変更せず `app/src/main/assets/conversion/sumire/` に収録。
  約 13.5 MB、展開した主要配列の元データは約 35.6 MB。
  プロセス全体にはトライ索引、Kuromoji、LM 等の追加メモリが必要。
- 人名・地名追加辞書、Wikipedia、新語、絵文字、英語、任意 n-gram 辞書は組み込まない。

## 移植時の変更

`SuccinctBitVector.kt`, `Node.kt`, `Other.kt` は上記 commit のソースをそのまま収録。
`GraphBuilder.kt` は元実装に未知のかなを保持する高コストノードを追加した。
これは通常の未知語処理であり、辞書のロード失敗を隠す代替変換ではない。
アセットが欠けたり壊れたりしていれば初期化は例外になる。

LOUDS と TokenArray は同じ保存形式・探索手順を使うランタイム部分の移植で、
ビルダー・圧縮書き出し・デスクトップパス依存を除き、boxed collection を primitive array
に置き換えた。読込例外を握りつぶさず、配列・品詞表の整合性を検証する。
トライ探索は接頭辞に一致しない時点で停止するよう修正した。
上流の `Extenstions.kt` から平仮名→片仮名変換を抽出し `ゔ` も処理する。

`FindPath.kt` は上流のラティスとコスト規約を引き継ぐ Viterbi/A* の移植。
接続コストには負値があるため、部分経路のコストだけを優先する上流の列挙方法を、
後向き Viterbi で求める正確な残コストを用いた A* に置き換えた。
探索量は 20,000 展開／キュー 10,000 経路に制限するため、極端に曖昧な読みでは
要求した候補数より少なくなることがある。入力は最大 64 文字、出力は最大 20 候補。
候補を重複排除し、64 エントリの LRU キャッシュを使う。

## 漢字表記の文脈評価

### 辞書だけで同音異義語の順序が決まる理由

処理順は、(1) 軌跡・ひらがなLM・読み辞書による読みの探索、(2) 辞書の
単語コストと品詞接続コストによる漢字候補生成、(3) 表記の文脈評価、
(4) 読みをまたいだ表示順位付け。同じ読みの「会う／合う」は(1)では区別できない。
従来は(3)がなく、(2)の辞書コスト順がそのまま残っていた。

実辞書での「ともだちにあう」の内訳は次のとおり（スケール前の整数値）。

| 表記 | 単語コスト合計 | 接続コスト合計（BOS/EOS込み） | 合計 |
| --- | ---: | ---: | ---: |
| 友達に合う | 5618 | 4935 | 10553 |
| 友達に会う | 6018 | 4935 | 10953 |

接続コストが同じなので、単語コストが400低い「合う」が優先される。
「先生にあう」「サイズにあう」でも辞書の差は400。
品詞のつながりだけでは具体的な名詞と動詞の使い分けを評価できない。

### 追加した処理

`SurfaceLanguageModel` は漢字かな交じりの文字1〜4-gramを評価する。
特定の読みや例文を照合する条件分岐・置換表は持たない。
[Tatoebaの日本語例文](https://downloads.tatoeba.org/exports/per_language/jpn/)から
NFKC正規化・重複排除・3〜256文字の長さ制限を行い、224,261文で学習した。
文のJava文字列ハッシュの剰余が0になる約10%（24,619文）は学習から除外。
短い文脈へ平滑化しながら、1文字あたりの平均負の対数確率を計算する。
文全体の確率の積で短い表記ばかりが有利になるのを避けるため平均を使う。

辞書の上位20候補を取得した後、要求された3件などに絞る**前**に再評価する。
旧3件枠より下にいる表記も比較可能になるが、20件より外の候補は救済できない。

```text
辞書コスト D = (単語コスト + 品詞接続コスト) × costScale
補正原値 r = weight × (LM平均コスト - 辞書第1候補のLM平均コスト)
加点側の縮小率 = min(1, maxAdjustment / 加点側の最大絶対値)
減点側の縮小率 = min(1, maxAdjustment / 減点側の最大絶対値)
文脈補正 Δ = r × その側の縮小率
変換コスト C = D + Δ
```

最大絶対値が0の側は縮小率1とする。コストを下げる負値が加点、上げる正値が減点。
候補ごとの切り詰めは行わない。例えば辞書第1候補が不自然な場合、複数の改善候補を
すべて-0.75に切り詰めると文脈評価の差が消え、再び辞書順位だけで並んでしまう。
同じ側を一律に縮小して候補間の差を残し、悪い候補が良い候補への加点まで弱めるのも避ける。

この不具合を「いがいたい」で再現した。切り詰め時は「以外たい」「位が痛い」「胃が痛い」
などが同じ-0.75となり、「胃が痛い」は7位でIMEに渡す3件から外れていた。
変更後は「胃が痛い」-0.75、「位が痛い」約-0.576、「以外たい」約-0.421と差が残り、
「胃が痛い」が第1候補になる。読み自体は辞書の未知語判定にも該当していなかった。
専用の単語ルールやモデルの再学習は使っていない。

`SurfaceRerankingConfig` の既定値は `weight = 0.5`、`maxAdjustment = 0.75`、
`maxDictionaryGap = 1.0`。辞書第1候補とのDの差が1.0を超える候補には補正しない。
重み0ならモデルを読み込まず、辞書だけの従来順位で返す。
最終表示では下記の式の「変換コスト」にCを使う。
`ConversionCandidate` はCに加え、`dictionaryCost`、`contextAdjustment`、
`wordCost`、`connectionCost`を返すので、順位の理由を追跡できる。

モデルはgzipで2,006,873バイト、主要な展開配列は約5.9MB。
格納名は `surface/model.bin`。Androidビルド時に `.gz` が自動展開・改名されるのを避け、
APK内でも同じgzipペイロードを保持する。投稿者情報は通常のZIPに格納する。
入力中の通信・ユーザー入力の学習や保存・追加のONNX推論は行わない。
前の確定文章は引き続き読みLMに使うが、この表記モデルは今回の候補文字列だけを評価する。
最大3文字の左文脈しか扱わず、意味を全面的に理解するモデルではない。

### 比較結果と再現

最初の30例で、辞書のみの第1候補一致は11件、文脈評価ありは25件。
補正の縮小方式を修正した後も25件を維持した。
`tools/conversion/evaluation.tsv` には「胃が痛い」「頭が痛い」「歯が痛い」を追加し、
現在の33例では辞書のみ13件、文脈評価あり28件。元から一致した13件はすべて維持した。
「友達に会う」「服を着る」「写真を撮る」「川で泳ぐ」などが改善した。
「友達に会った」は5位→2位で、第1候補は依然「友達にあった」。
「鼻が痛い」は3位→4位と悪化し、旧3件枠に入っていた候補が外れる例もある。
「飴をなめる」「荷物を載せる」なども第1候補にはならない。

これは正しい読みを直接渡す33例の回帰比較で、実機の軌跡認識率や一般的な
変換精度の推定ではない。評価例を学習スクリプトは読み込まないが、例文コーパスとの
重複は排除していないため、独立した未知文章の評価とも主張しない。
テストは `app/build/reports/conversion-ranking.tsv` に全例の順位を出力する。
同ファイルの時間はJVM単発測定でキャッシュ・JITの影響があり、速度比較には使わない。

```powershell

# 固定SHA-256の元データを再利用／取得して学習を再現（Java 17以降・bzip2が必要）
./tools/conversion/prepare_surface_model.ps1
./gradlew.bat :app:testDebugUnitTest --tests '*SumireKanaKanjiConverterTest'
```

取得元は毎週更新されるため、別の版ならSHA-256照合で停止する。
再現用の固定ハッシュ・学習件数は `tools/conversion/surface-model.json` に記録した。
学習元のライセンスはCC BY 2.0 FRで、モデルにも同ライセンスを適用する。
`licenses/TATOEBA-NOTICE.md`と、学習文ID・投稿者の対応を収録した
`licenses/TATOEBA-ATTRIBUTION.tsv.zip`をAPKに同梱する。

## 最終候補の順位付け

`GlideCandidateEngine` は各読みから最大3件の変換候補を取得し、読みをまたいで
次のスコアが高い順に並べる。

```text
表示スコア = ReadingCandidate.score
           - 読み間の表記文脈ペナルティ
           - conversionCostWeight × (変換コスト - 同じ読みの最良変換コスト)
```

変換コストは単語・品詞接続・BOS/EOSの生コストに `SumireLexiconConfig.costScale`
（既定 `1 / 5000`）を掛け、上記の文脈補正を加えた値。`conversionCostWeight` の既定値は `1.0`。
各読みの最良変換から、異なる読みとも比較可能な平均負対数確率 `surfaceCost` を取得する。
その最小値との差に `readingSurfaceWeight`（既定0.5）を掛け、
`maxReadingAdjustment`（既定0.75）までのペナルティを、その読みの全表記に適用する。
表記モデルがない読みは補正しない。読みごとに基準が違う `contextAdjustment` は読み間比較に流用しない。

読みスコアには既に辞書評価が含まれるため、変換の絶対コストを再加算せず、
同じ読みの最良候補からの差だけを使う。読み側の語境界ペナルティと後段の
変換コストは引き続き異なる評価であり、この式は確率ではなく順位付けの近似。
語分割の探索・辞書データ・読み探索の順位は変更しない。重みは実入力による調整が必要。

かな表記にも読み間ペナルティを適用し、同点なら読み順位・変換器内の順位で
安定して並べる（かな表記は同じ読みの同点の変換候補の後）。
同一表記は最も高い表示スコアを残す。
最大12件のうち、最上位候補、最上位の読みそのもの、別の読みの候補1件を
この順を基本に、最上位の元の読みの直後には連続文字補完を含む読みのかな表記も確保する。
さらに最良表示スコアから `readingDiversityWindow`
（既定2.0）以内にある異なる読みの代表を最大3件確保し、残りをスコア順で埋める。
表示ではこの代表を先頭に並べ、その後に残りをスコア順で並べる。
近い読みの解釈が同じ読みの表記違いに埋もれないようにするためで、
全表示が厳密なスコア順になるわけではない。未知文字を含む読みも変換し、
未知のかなを保持しながら既知の部分を変換する。元の読みも候補に残す。

「いかかいたい」「いがいたい」の固定読み候補では、僅差なら表記文脈によって
「胃が痛い」が先頭になり、読みスコア差が1.3なら買い物の候補を先頭に保ちつつ両方を上位に残す。
2026-09-15に接続端末の実モデルと「いかいたい」をなぞる2種類の合成軌跡で
「胃が痛い」が表示2位になることを確認した。JVM 73件、Android 4件も成功。
AndroidテストはGradle経由だとオフライン依存が不足したため、ビルド済みAPKを
`adb install -r` で更新して `am instrument` で実行した。
実際のユーザー軌跡は未取得であり、
読みが探索の途中で消えた場合やスコア差が大きい場合の救済は保証しない。

`GlideCandidateEngineTest` は、有力な読みの第2・第3候補の繰り上げ、
大きなコスト差による順位逆転、絶対コストの二重評価防止、表記重複、
件数制限下のかな・別読み保持、未知語、同点時の安定順序を検証する。

## 候補の背景色

`GlideCandidateEngine` は、同一表記を最良スコアで重複排除した後の全候補に対して
`exp(score - bestScore) / Σ exp(score - bestScore)` を計算し、`DisplayCandidate.confidence`
としてUIへ渡します。件数制限や読みの代表を先頭に並べる処理より前に正規化するため、
表示件数や表示位置だけで色は変わりません。表示候補だけの合計は1未満になることがあります。
通常の2行表示と展開一覧で同じ値を使い、低いほど薄い青、高いほど薄い緑になります。

これは探索・変換の近似スコアを正規化した相対的な支持度です。探索から落ちた候補を
含む確率でも、実入力で校正した正解率でもありません。スコアを返さないテスト用などの
エンジンでは確からしさをnullとして白背景を使います。

## グライド探索中の辞書スコア

`SumireKanaKanjiConverter.readingLexicon` は、漢字変換用に読み込んだ読みトライ、
単語コスト、品詞接続行列を共有する。追加の辞書ファイルや二重ロードは不要。
`SumireReadingLexicon` のセッションをグライドのデコードごとに作り、
読み候補をビームから落とす**前**に `evaluate(reading, complete)` を呼ぶ。
A の軌跡評価は意味に依存しないまま、混合スコアから `dictionaryWeight × cost` を引く。
`cost` は小さい方が良い辞書の評価値で、正規化された確率ではない。

探索は直前の読み状態から一文字ずつトライを進め、単語末尾ごとに
単語コスト・前後の品詞接続コスト・語境界ペナルティを加算する。
同じ読み・左右品詞の表記違いは最小コストにまとめる。
単語を一つに限定せず、活用形や助詞を含む複数語の経路も比較する。
完成した入力では EOS への接続も採点し、単に辞書に接頭辞があるだけの読みは
完成語とはみなさない。

途中の読みは、まだ続く辞書語の接頭辞であれば「語境界＋文字数に比例する仮コスト」で
維持する。長い単語が末尾に到達する前に落ちることを防ぐための近似であり、
将来の語コストを保証する A* 下界ではない。
辞書にない一文字を通る高コスト経路も常に用意し、その経路で消費した文字数を返す。
未知の名前や新語を禁止する機能ではなく、既知の語・接続を優先する機能である。

調整値は `SumireLexiconConfig` で指定できる。

| パラメータ | 初期値 | 意図 |
| --- | ---: | --- |
| `costScale` | `1 / 5000` | 辞書コスト 5000 を混合スコアの 1 点にする |
| `wordBoundaryCost` | `1500` | 短い語を無理に多数つなぐ経路に 1 語あたり 0.3 点加算 |
| `unknownCharacterCost` | `20000` | 未知の一文字に 4 点＋境界分を加算 |
| `unfinishedCharacterCost` | `1000` | 未完の辞書語を一文字 0.2 点で暫定評価 |
| `maxCachedPrefixes` | `256` | デコードごとの読み状態 LRU 上限 |
| `maxCachedTokenReadings` | `512` | デコードごとの品詞・最小単語コスト LRU 上限 |
| `maxPosStates` | `64` | 各読み末尾に残す右品詞状態の上限 |

値は初期の調整用であり、実機の雑な軌跡で最適化した値ではない。
接続コストに負値があるため、右品詞状態の上限に達した場合は厳密な最短経路を
取り逃す可能性がある。探索スコア用の読みは最大 128 文字に制限し、デコードのキャンセルを確認する。
後段の漢字変換の上限は引き続き 64 文字で、IME のデコーダは既定で最大 32 文字を使う。
全語彙走査や読みごとの N-best 漢字変換は行わず、セッションを破棄すればキャッシュも消える。

## 文脈の読み

[Kuromoji IPADIC 0.9.0](https://github.com/atilika/kuromoji/tree/0.9.0)
を Maven Central から依存として取り込む（辞書込み約 13 MB の JAR）。
`Token.reading` を平仮名化し、助詞「は」「へ」などの表記を維持する。
発音フィールドは使用しない。未知語は元表記を残し、LM のトークナイザ側で扱う。
人名などの多義的な漢字の読みは形態素解析による推定なので必ずしも正解にならない。

## 再取得と検証

```powershell
./tools/conversion/prepare_sumire.ps1 -VerifyOnly
./tools/conversion/prepare_sumire.ps1
./gradlew.bat :app:testDebugUnitTest --tests '*conversion.*'
./gradlew.bat :app:connectedDebugAndroidTest
```

通常のビルドでは再取得不要。5 ファイルはすでに同梱済み。
取得スクリプトは固定版の公式配布アーカイブと各抽出ファイルの SHA-256 を検証する。
テストは本物の同梱辞書で「にほんご→日本語」、複数語、未知のかな、文脈読みを検証し、
負の接続コストを持つラティスの候補順も確認する。
読みの辞書スコアも実辞書の既知語・活用・複数語・未知かなで検証する。
小さな合成辞書では、未完接頭辞と完成語の区別、単語・品詞・EOS のコスト、
語の分割、同品詞トークンの集約、キャッシュ上限、割り込みを確認する。
Android instrumentation は APK 内の ZIP と Kuromoji 辞書の classloader 経由読込を確認する。
