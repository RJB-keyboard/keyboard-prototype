# 変換時間の調査

## 計算再利用の変更（2026-09-15）

連続文字補完の複数段階の確率を、同じONNX推論の異なる位置から取り出すようにした。
例えば「ごま」と「ごまま」の次かな分布を、「ごまま」を入力した1回の推論から得る。
途中位置は後続文字を参照しないため、入力トークンと位置番号が一致すれば同じ条件付き確率になる。
詳細は [連続文字補完の確率をまとめて取得](hiragana-model.md#連続文字補完の確率をまとめて取得) を参照。

探索する読み、ビーム幅、連続文字補完数、文脈上限、スコア式は維持する。
先読みの結果はdecode内キャッシュに追加し、従来と同じ順序で枝刈りする。
未対応のモデル実装は従来の分布取得へフォールバックする。
96トークンの切り詰めで文脈の先頭が変わる場合も従来の計算を使う。
長い前文脈の毎回の再計算を解消する変更ではない。

繰り返し上限・読み長上限・異なる文脈・不正なプロバイダー応答も確認する。

### 前後比較の再現

`RepeatedInferenceInstrumentedTest` は同一の実モデル・辞書に対し、
従来の単独分布APIだけを使うアダプターと、複数位置の分布を返すアダプターを比較する。
通常の5秒制限を超える条件の完了結果も比較するため、診断中だけ制限を120秒に延長する。
タップ、挨拶、短い前文脈、連続文字、痛みの表現を各1ペアウォームアップ後、
前後の実行順を交互にして各3ペア測定する。長い前文脈は再計算へのフォールバックを1ペア確認する。
読み探索と最終変換・順位付けの合計時間を記録し、モデル初期化、前文脈をかなに戻す処理、
ワーカーの待ち行列、UI描画は含めない。変換器のメモリー内キャッシュは前後で共有する。

```sh
./gradlew :app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=net.ramdos.keyboard_prototype.RepeatedInferenceInstrumentedTest \
  -Pandroid.testInstrumentationRunnerArguments.profileRepeatedInference=true
adb exec-out run-as net.ramdos.keyboard_prototype cat files/repeated-inference.jsonl \
  > /tmp/repeated-inference.jsonl
```

各ペアで読み候補の順序、表示候補の順序、Aのスコア、辞書コスト、連続文字補完フラグを比較する。
モデル呼び出し回数は増えないことを確認するが、実行時間の合否閾値は設けない。
実モデルのバッチ形状が変わるため、浮動小数点のビット単位の一致は要求しない。
`OnnxHiraganaLanguageModelTest` では独立した推論との次かな対数確率差を2e-4以内、
前後比較では読み全体の言語スコア差を0.003以内、結合スコア差を0.0011以内、
posterior差を0.0002以内で確認する。
一般の実入力精度を統計的に保証する評価ではなく、計算再利用の同値性と合成軌跡の回帰確認である。

## 実装前の調査結果（2026-09-15）

**主な待ち時間は、読み候補探索中のモデル呼び出し。長い前文脈では特に大きい。**
かな漢字変換そのものの時間は、今回の条件では小さかった。
また、最初の入力にはモデル・辞書初期化の約2.4秒が加わる。

対象は `c7951ef` の実装、Pixel 8 / Android 17（API 37）、debug APK、
実ONNXモデル・実辞書。モデルのSHA-256はコード内の固定値と一致。
端末のモデルファイルは配置済みで、初回コピー・ハッシュ検証の時間は含まない。
充電なし、計測準備時のバッテリー温度32.8℃、終了後34.9℃。
CPUクロックや他アプリの負荷は固定していない。
元データは [conversion-latency-pixel8.jsonl](conversion-latency-pixel8.jsonl)。

### 初回とキャッシュ

モデル初期化は451.5ms、辞書・変換器初期化は1,935.8ms、合計2,387.3ms（各1回）。
辞書・変換器にはSumire辞書、表記モデル、Kuromojiの初期化を含み、
その中での時間配分は今回分離していない。
最初のタップの候補生成119.1msを足すと約2.51秒になる。
これはエンジン側の合算であり、実際のUI表示までの時間ではない。

各条件を初めて通したときのかな漢字変換は、タップ35.6ms、挨拶138.7ms、
短文脈付き41.4ms、長文脈付き9.3ms、補完無効14.1msだった。
条件間でも同じ読みのキャッシュを共有するため、すべてが完全なキャッシュなしの値ではない。
繰り返し時の約0.2〜0.3msだけを一般的な漢字変換速度とは解釈しない。

### 改善を検討する順序

1. **モデルが同じ前文脈を繰り返し計算する量を減らす。**
   長文脈の入力長と、中間計算結果の再利用を検討する。
   入力長の短縮は文脈による順位への影響、中間結果の再利用はモデル入出力の対応を別途検証する。
2. **連続文字補完を含む探索のモデル呼び出し数を減らす。**
   単純な補完無効化には欠落する候補があるため、補完を残した枝刈り・評価方法を検討する。
   文字抜けと不要な文字追加の両方の回帰確認が必要。
3. **初回の約2.4秒を減らす、または入力前に準備する。**
   メモリー使用量・キャンセル・初期化失敗の扱いを保つ必要がある。
4. **探索中の辞書評価を改善する。**
   挨拶では約336msあり、モデルに次ぐ対象。キャッシュの効果を追加計測して判断する。

この調査時点では計測テストと調査記録だけを追加し、候補生成・順位付け・制限時間の製品設定は変更していない。
Gradle Wrapperによる単体テスト102件、Lint、debug APK・端末テストAPKのビルドが成功。
追加した性能診断は上記端末で成功し、5条件×8回の40サンプルを記録した。
既存UI・精度の端末テストは今回再実行していない。

## 調査時に特定した実装箇所

1. [`OnnxHiraganaLanguageModel.nextLogProbabilities`](../app/src/main/java/net/ramdos/keyboard_prototype/engine/lm/OnnxHiraganaLanguageModel.kt)
   は、毎回 `context + prefix` を最大96トークンまで入力し、ONNXを実行する。
   入出力は `input_ids / attention_mask / position_ids → logits` で、
   共通する前文脈の中間計算結果を次の推論へ引き継ぐ仕組みはない。
   同じ呼び出し内でもバッチの最長入力に合わせてパディングする。
   最後の位置の確率だけ取り出しても、前の位置のモデル計算は毎回発生する。
2. [`GlideDecoder`](../app/src/main/java/net/ramdos/keyboard_prototype/engine/GlideDecoder.kt)
   は各イベントの通常展開に加え、最大3連続文字の補完を探索する。
   prefixごとの出力キャッシュで同じprefixの重複推論は避けるが、
   当初は別prefixが共有する前文脈の計算は再利用していなかった。
   上記変更後は連続文字補完の途中位置の出力を利用する。
   通過キーもイベントになるので、入力しようとした文字数よりイベント数が多くなる。
3. [`SumireReadingLexicon`](../app/src/main/java/net/ramdos/keyboard_prototype/engine/conversion/SumireReadingLexicon.kt)
   は通常展開・補完の両方で多数の候補を評価する。
   既定のprefixキャッシュは256件で、1回の読み探索内だけ有効。
   キャッシュの退避による再計算量は今回の計測では分離していない。
4. [`CandidateSession`](../app/src/main/java/net/ramdos/keyboard_prototype/engine/CandidateSession.kt)
   は最初のリクエスト時にエンジンを生成する。
   [`JapaneseInputMethodService`](../app/src/main/java/net/ramdos/keyboard_prototype/JapaneseInputMethodService.kt)
   の生成処理はモデルと辞書を順に開くので、その合計も初回の待ち時間になる。

通常の読み探索は5秒で打ち切る設定だが、時間を確認するのは処理の区切り。
進行中の `nextLogProbabilities` に対して5秒ちょうどでタイマーが割り込む構造ではない。
新しい入力によるキャンセルは別途ONNXへ中断要求を送る。
候補生成全体や初期化の5秒保証でもない。

## 計測方法

`ConversionLatencyInstrumentedTest` は明示的に有効にしたときだけ動く性能診断。
実ONNXモデル・実辞書を使い、`GlideCandidateEngine.generateCandidates` の
経過時間を次の内訳に分ける。通常のIMEにログや計測処理は追加していない。

- **モデル呼び出し**: `nextLogProbabilities`。入力のトークン化、テンソル作成、
  ONNX推論、出力確率の取り出しを含む。ネイティブ演算だけの時間ではない。
- **探索中の辞書評価**: `ReadingLexicon.newSession` と `evaluate` の累計。
- **前文脈の読み取り**: Kuromojiで文章をかなへ戻す `readingOf`。
  入力先アプリから文章を取得する時間は含まない。
- **かな漢字変換**: 最大8読みの `convertCandidates` の累計。
  辞書ラティス構築、N-best探索、表記モデルでの順位付け、キャッシュ参照を含む。
- **その他**: 全体から上記を引いた残り。軌跡の格子化、ビーム展開・ソート、
  最終順位付け、計測の付加コストなど。単一の処理時間とは解釈しない。

モデルと辞書の初期化は別に計測する。IMEでは `CandidateSession` が最初の依頼で
これらを遅延生成するため、初回は初期化時間も待ち時間に加わる。

軌跡は各キー中心に180ms滞留し、次のキーまで120msで移動する合成データ。
タップ、挨拶、短い前文脈と長い前文脈での同一軌跡、連続文字補完を無効化した比較を使う。
各条件の初回を記録した後、条件を交互に2巡ウォームアップし、5巡計測する。
かな漢字変換の64件LRUキャッシュは保持するため、同じ入力を繰り返した温まった状態での値。
初回の値も比較し、実利用の毎回異なる入力と区別する。

計測中は読み探索の制限時間だけ120秒に延長し、通常の5秒を超える負荷も観測する。
他の既定設定は維持する（連続文字補完無効の比較条件を除く）。
`overDefaultBudget` は候補生成全体が5秒以上かの参考値であり、
読み探索だけに適用される製品のタイムアウト判定とは異なる。
時間に関する合否の閾値は設けない。

## 再現

[開発手順](development.md#ビルド準備)に従いモデルを用意する。
接続先が複数の場合は `ANDROID_SERIAL` で計測する端末を指定する。

```sh
./gradlew :app:connectedDebugAndroidTest \
  -Pandroid.testInstrumentationRunnerArguments.class=net.ramdos.keyboard_prototype.ConversionLatencyInstrumentedTest \
  -Pandroid.testInstrumentationRunnerArguments.profileConversion=true
adb exec-out run-as net.ramdos.keyboard_prototype cat files/conversion-latency.jsonl \
  > /tmp/conversion-latency.jsonl
```

ビルド済みAPKを使う場合:

```sh
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb shell am instrument -w -r \
  -e class net.ramdos.keyboard_prototype.ConversionLatencyInstrumentedTest \
  -e profileConversion true \
  net.ramdos.keyboard_prototype.test/androidx.test.runner.AndroidJUnitRunner
```

出力はアプリ内 `files/conversion-latency.jsonl` とlogcatの `ConversionLatency` タグ。
テストで生成した条件名、時間、件数だけを記録し、ユーザーの文章・軌跡は収集しない。
JSONLは実行ごとに上書きする。

## 限界

これは実端末での合成軌跡のエンジン計測であり、実際の指の入力の精度や、
指を離してから画面に候補が描画されるまでの時間を保証するものではない。
IMEワーカーの待ち行列、前の推論のキャンセル待ち、入力先とのIPC、
UIスレッドの配送・描画は計測対象外。CPUスケジューリング、GC、JIT、端末温度は経過時間に影響する。
連続文字補完無効の比較は探索量の影響を見る診断で、精度を維持した高速化案ではない。
